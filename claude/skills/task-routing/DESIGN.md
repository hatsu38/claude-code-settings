# task-routing 設計メモ(2026-07-19)

## 目的

メインセッション(高性能モデル)を統括役に固定し、探索・計画・実装・レビューを役割ごとに最適なモデル/ツールへ委譲する規範を常時適用する。実装(diff を書く作業)は Codex に委譲する。

## 採用した構成

- 単一スキル(`SKILL.md`)+ ルーティング表(`routing.md`)。モデル名は routing.md にのみ記載し、新モデル登場時は表の編集だけで乗り換え可能にする
- 常時適用の補強として `~/.claude/CLAUDE.md` に 1 行追記(スキル自動起動は description マッチ依存のため)
- 実行部品は既存を再利用: Agent ツールの model パラメータ、openai-codex プラグインの `codex:codex-rescue`、プロジェクトのレビュアーエージェント

## 却下した代替案

- **フルプラグイン化(agents + hooks)**: 使う部品が全て既存のため過剰。管理コスト高
- **CLAUDE.md にルールを直書き**: 全セッションでコンテキストを常駐消費し、Codex 呼び出し手順など詳細を書くと肥大化する

## ベースラインテストで観測した失敗(スキルが塞ぐ穴)

1. 「コード量が少ないから」「骨組みだけだから」と実装を自分で書く(Codex に機械的作業しか回さない)
2. デバッグ分析を自分でやる(分析役に出さない)
3. サブエージェントの model パラメータを省略する(使い分けが発生しない)

→ SKILL.md の Red Flags 表と手順 3 で明示的に対処。

## テスト方法のメモ

haiku サブエージェントに「スキル本文を Read させた上で」シナリオの進め方を答えさせ、ルーティングが表と一致するか検証した。スキル本文を Read させず口頭指示だけにすると、エージェントは内容を想像で補って回答する(tool_uses: 0 になる)ので無効。routing.md を変更したら同じ方法で再検証すること。
