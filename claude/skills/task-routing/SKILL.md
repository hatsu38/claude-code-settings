# Task Routing(モデル・ツールの使い分け)

## Overview

メインセッションは**統括者であり実装者ではない**。作業は役割ごとに分解し、最適な実行先(モデル指定つきサブエージェント、Codex)へ委譲する。

役割→実行先の対応は同ディレクトリの **[routing.md](routing.md) が唯一の真実(SSOT)** で、モデル名・ツール名はそこにしか書かない。新しいモデルが登場したら routing.md の表を書き換えるだけで全セッションの挙動が変わる。本ファイルにモデル名を書き足してはいけない。

## 手順

1. `~/.claude/skills/task-routing/routing.md` を Read する(表を記憶に頼らない。表は更新されうる)
2. **最初に例外判定**: 依頼が routing.md の「小修正閾値」に収まる機械的変更なら、委譲せずメインセッションが直接実行して終了する(下の「直接実行してよい例外」参照)。閾値を超える、または収まるか不確かなときだけ手順 3 へ
3. タスクを役割に分解する: 探索・調査 / 計画・分析 / 実装 / レビュー / 統括・検収
4. 各役割を表の実行先に委譲する。**サブエージェント起動時は必ず model パラメータを表のとおり明示する**(省略するとメインと同じモデルが使われ、使い分けにならない)
5. 独立した委譲は 1 メッセージで並列に出す
6. 委譲結果はメインセッションが必ず検収する: diff 確認 → lint / type check → 必要なら動作確認。検収なしのコミットは禁止

## 直接実行してよい例外(これ以外は委譲)

- 会話・質問への回答のみで、ファイル変更を伴わない
- **小修正**: routing.md の「小修正閾値」以内の機械的変更(typo、import パス修正、設定値の変更など)
- 委譲結果の検収で見つけた、小修正閾値以内の手直し
- git 操作・コマンド実行・ドキュメント(.md)編集などの統括業務

例外は上記に列挙されたものだけ。「今回は特別」は例外ではない。

## 実装を Codex に委譲するときの要点

- Agent ツールで `subagent_type: "codex:codex-rescue"` を起動し、実装内容を自己完結した文面で渡す(対象ファイルパス・期待する振る舞い・従うべき規約を含める)
- 実装が複数ステップ・長時間になりそうなら background、明確で小さければ foreground
- 「新機能の骨組みだけ」「バグ修正だけ」のような**部分的な実装も Codex の担当**。機械的な一括変換だけを回す先ではない
- 委譲文面が書けないほど仕様が曖昧なら、先に計画・分析役(routing.md 参照)に整理させてから委譲する

## subagent-driven-task-execution との併用

両方が発動した場合: 実行構造(サブエージェント駆動)はそちらに従い、**各サブエージェントの model 指定と実装作業の Codex 委譲は本スキルの routing.md に従う**。矛盾する場合は routing.md が優先。

## Red Flags — 直接実装しかけているサイン

| 思考 | 現実 |
|------|------|
| 「コード量が少ないから自分で書いた方が速い」 | 小修正閾値を超えるなら委譲する。速度ではなく検収体制(書く人と検収する人の分離)が目的 |
| 「1 行の修正でも一応 Codex に出しておくか」 | 逆方向の誤り。小修正閾値以内なら直接実行が正しい。委譲は手段であって目的ではない |
| 「骨組み/雛形だけ自分で作る」 | 骨組みも実装。Codex に「骨組みを作って」と委譲する |
| 「バグの原因は自分で調べた方が早い」 | デバッグ分析は表の分析役へ。メインは仮説の検収に徹する |
| 「Codex に説明する方が手間」 | 説明が書けない=仕様が曖昧。先に計画役に整理させる |
| 「探索くらい自分でやる」 | 探索はコンテキストを大量消費する。表の探索役に出して結論だけ受け取る |
| 「model 指定は省略でいいか」 | 省略するとメインと同じモデルになる。必ず表のとおり明示する |
